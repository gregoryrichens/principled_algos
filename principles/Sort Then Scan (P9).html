Principled Algos · Principle 9 of 18

Sort Then Scan

Put the items in order. Then each item only has to look at its neighbor.

P1 is "hash it", P5 is "two pointers" and P7 is "greedy". Card 14 in DRILLS.md drills this page.

As if to a child

Your class wants to know if two kids have the same birthday. One way: each kid asks every other kid. With 30 kids, that is 435 questions.

A better way: the kids stand in a line in calendar order, January 1 at the front and December 31 at the back. Now two kids with the same birthday must stand side by side. Each kid asks only the kid in front: 29 questions. To make the line is also work, but it is much less work than 435 questions.

The extended explanation

Start from what is true

  • Fact 1. There are many pairs. With n items there are n × (n − 1) ÷ 2 pairs: 435 for 30 kids, about 50 million for 10,000 items.
  • Fact 2. After a sort, equal items stand side by side. If a[i] = a[j] in a sorted list, any a[k] between them has a[i] ≤ a[k] ≤ a[j], so it is the same number too.
  • Fact 3. A sort costs about n × log2 n comparisons. log2 n is how many times you can cut n in half before you get to 1: about 13 for 10,000. Merge sort (John von Neumann, 1945) cuts the list in half again and again, then joins the parts back in order. Each of the log2 n levels of joins puts all n items in place with about one comparison each.

Join the facts: sort once, then compare each item only with its neighbor. For 10,000 items that is about 133,000 + 10,000 ≈ 143,000 steps, not 50 million. Here is Fact 2 as code, for Contains Duplicate (LeetCode 217):

def containsDuplicate(nums):
    nums = sorted(nums)
    for i in range(1, len(nums)):
        if nums[i] == nums[i - 1]:      # a copy can only be the item just before
            return True
    return False

Intervals: the same idea on a number line

An interval is a pair [start, end], like a meeting from 2 to 6. Two intervals overlap when they share a point. On this page, intervals that touch, like [1, 3] and [3, 5], overlap.

Sort the intervals by start. That gives Fact 4: every later interval starts at or after the current one. Go through the list once, and keep the open block: the merged interval that you build now. For each new interval, ask: does it start at or before the end of the open block?

  • Yes. By Fact 4, it also starts at or after the block start. So it starts inside the block and overlaps it. Make the end of the block the larger of the two ends.
  • No. It starts after the block ends. By Fact 4, all later intervals start later still, so none can reach back. The block is finished, and the new interval opens a new block.

Both answers use Fact 4. Without the sort, a "yes" can be false, and a closed block can still get an overlap later.

Bars are intervals in list order. Amber: the interval now. Grey: done. Blue: the open block. Teal: finished blocks (grey in the unsorted run, where the code cannot know). Dashed line: the start of the interval now; by Fact 4, every bar below starts on it or to its right.

Now press Scan without sorting. The code says that [1, 3] overlaps [8, 10], which is false, so [1, 3] is lost.

The sentence that keeps the code correct

Each earlier interval is covered by a block in merged. The blocks are in order and do not overlap. Only the last block can still grow.

This is the invariant: a statement that is true at the start of each loop turn. Fact 4 keeps it true, because a new interval can only touch the last block. When the loop ends, every interval is covered by blocks that do not overlap. That is the answer.

Worked example 1: Merge Intervals (LeetCode 56)

Problem. Merge all overlapping intervals. With the widget data: [[8, 10], [1, 3], [15, 18], [2, 6], [9, 12], [5, 7]] → [[1, 7], [8, 12], [15, 18]].

def merge(intervals):
    intervals.sort()                       # by start
    merged = []
    for start, end in intervals:
        if merged and start <= merged[-1][1]:
            merged[-1][1] = max(merged[-1][1], end)   # overlaps the open block: extend it
        else:
            merged.append([start, end])    # starts after the block ends: a new block
    return merged

Why max? A new interval can be fully inside the block ([1, 10], then [2, 5]). Without max, the block shrinks to [1, 5].

Worked example 2: Meeting Rooms II (LeetCode 253)

Problem. Return the fewest rooms that hold all the meetings, with no two at the same time in one room. A room freed at time t can hold a meeting that starts at t.

The idea. You need as many rooms as the largest number of meetings in progress at one time. That many is enough: when a meeting starts, the count with it is at most the largest count, so a room is free. Change each meeting into two events: +1 at its start and −1 at its end. Sort the events by time, go through them, and keep a count. This is a sweep line: a vertical line moves from left to right and counts the meetings that it crosses.

Ties. At time 10 below, A ends and B starts. If the end comes first, A's room is free before B needs it. Python sorts (10, -1) before (10, 1), so the sort does this with no extra code. Set "start first" to see the wrong count.

Chips: the sorted events as (time, change) and meeting. Blue bars: in progress. Grey: ended. Amber: the sweep line. The chart shows the count after each event, and its dashed line is the largest count (red when it is wrong).

def minMeetingRooms(intervals):
    events = []
    for start, end in intervals:
        events.append((start, 1))          # a meeting starts
        events.append((end, -1))           # a meeting ends
    events.sort()                          # at equal times, -1 comes before +1
    in_progress = most = 0
    for _, change in events:
        in_progress += change
        most = max(most, in_progress)
    return most

Worked example 3: the same sort, a different question (LeetCode 435)

Problem. Return the fewest intervals to remove so that the rest do not overlap. Here, touching is permitted. [[1, 2], [2, 3], [3, 4], [1, 3]] → 1.

The trap. It looks like Merge Intervals, but it tells you to choose intervals, not to join them. A merge makes [1, 2] and [1, 3] into one block, and then you cannot say which one to remove.

The rule. Sort by start. Keep prev_end, the end of the last interval that you keep. The kept intervals are in order and do not overlap, so prev_end is the largest kept end. A new interval that starts at or after it is clear of all of them. On an overlap, remove one interval and keep the one with the smaller end.

Why is that safe? Take a best answer that keeps the interval with the larger end, and put the one with the smaller end in its place. By Fact 4, each later interval that was clear of the larger end is also clear of the smaller end. So the answer stays as good. P7 proves greedy choices with this kind of swap.

def eraseOverlapIntervals(intervals):
    intervals.sort()
    removed, prev_end = 0, float("-inf")
    for start, end in intervals:
        if start >= prev_end:
            prev_end = end                 # no overlap: keep it
        else:
            removed += 1                   # overlap: remove the one that ends later
            prev_end = min(prev_end, end)
    return removed

Napkin math: how much faster?

The slider assumes 109 simple steps each second (fast compiled code). Python is about 100 times slower (see Claim 2).

Claim 1, from the P9 notes in PRINCIPLES.md: a sort is "only slightly more than one pass." For n = 100,000, sort and pass are about 1.7 + 0.1 million steps, 18 times one pass. But in Python 3, on the machine that built this page, the sort of 100,000 numbers took 18 milliseconds and one Python pass 7.5: only 2.4 times more. Python sorts in fast C code but runs the pass one slow step at a time. Verdict: exaggerated by step count, approximately accurate by clock time in Python.

Claim 2, a common rule: "for 10,000 items, every pair is too slow in Python." On the same machine, Python did about 9 million pair checks each second: 50 million ÷ 9 million ≈ 5.5 seconds. Sort and one pass took 9 milliseconds, about 600 times faster. Verdict: approximately accurate.

How to recognize it

  • [start, end] pairs with "merge", "overlap", "rooms" or "free time".
  • "Are two items equal, too close, or in conflict?"
  • A one-time choice (greedy, P7) that is safe only in one order: by end, by size, by position.
  • Not a hash (P1) when you need "close to" or "overlaps". A hash finds only equal values.

Common mistakes

  • A merge when the question says choose. "Fewest to remove" and "most to keep" ask for a choice.
  • The wrong tie order in a sweep line. Decide if an end and a start at one time overlap, and sort the events to match.
  • No max when you extend a block.
  • A change to a tuple. merged[-1][1] = ... needs a list, so append [start, end].

Try it yourself

Do each one before you open the answer.

1. Merge [[1, 4], [4, 5]]

Touching counts as overlap: 4 ≤ 4. Answer: [[1, 5]].

2. Merge [[1, 10], [2, 5], [6, 7]]

max keeps the end at 10. Answer: [[1, 10]].

3. Meeting Rooms (252): can one person go to all of [[0, 30], [5, 10], [15, 20]]?

Sort by start. Each meeting must start at or after the end of the one before it. 5 < 30, so no.

4. Rooms needed for [[1, 5], [5, 9], [2, 6]]

Events: (1, +1), (2, +1), (5, −1), (5, +1), (6, −1), (9, −1). Counts: 1, 2, 1, 2, 1, 0. Answer: 2. Put these numbers in the second widget and set "start first": it says 3.

5. Fewest removals for [[1, 2], [1, 2], [1, 2]]

Keep the first. The second and third overlap it (1 < 2), so remove both. Answer: 2.

In the real world

A Unix tool from the 1970s. Unix, made at Bell Labs, has a small tool called uniq. It removes a repeated line only when the copies are next to each other, and its manual tells you to sort the input first. So sort names.txt | uniq is Fact 2 as one command.

Databases. To match the rows of two tables by a key, a database can use a sort-merge join: sort both tables by the key, then go down both at the same time, with one pointer in each (P5). For 1 million rows in each table, every pair is 1012 comparisons. Two sorts are 2 × (106 × 20) = 4 × 107, plus 2 × 106 for the walk: about 4.2 × 107. Claim: "a sort-merge join can be thousands of times faster than every pair." 1012 ÷ (4.2 × 107) ≈ 24,000. Verdict: approximately accurate for big tables with no index.

Calendars. "Find a time when all 8 people are free" is Merge Intervals. Put all their busy times in one list, sort by start, and merge. The free times are the gaps between the blocks, and the time before the first block and after the last, inside the workday.
