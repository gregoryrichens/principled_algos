Heap

Keep the smallest item at the top. When the pile changes, fix one short path, not the whole order.

Card 15 in DRILLS.md drills this page.

As if to a child

A school nurse gives each sick kid a number: 1 is very sick, 9 is a little sick. She always sees the smallest number next. Kids come all day, so she does not sort the whole line each time.

She makes a pyramid. Each kid stands on top of kids with bigger numbers, so the smallest number is always at the top. A new kid starts at the bottom and swaps up while his number is smaller than the number above him. When the top kid leaves, the last kid goes to the top and swaps down with the smaller of the two kids below him. 1,000 kids make only 10 rows, so a change is 10 swaps or less.

The extended explanation

Start from what is true

  • Fact 1. Many programs ask again and again: "Which item is the smallest now?" Between questions, items come and go.
  • Fact 2. The easy tools are slow. In a list with no order, you look at all n items to find the smallest. In a sorted list, the smallest is at the front, but to remove it or to put a new item in place, Python moves up to n items.
  • Fact 3. A full order is more than you need. A sorted list also knows the 900th item, and you pay for that at each change.
  • Fact 4. A tree with two children under each item is short. Each row doubles, so n items fill about log2 n rows: 10 for 1,000 items, 20 for 1,000,000.

Join the facts. Use a tree, and keep only a weak rule: each parent is smaller than or equal to its children. Then the smallest item is at the top. A change can break the rule only along one path from top to bottom: at most 20 items for a million.

A tree that is only a list

Put the items in a list, row by row, from left to right. Then the item at index i has its children at 2i + 1 and 2i + 2, and its parent at (i − 1) // 2. J. W. J. Williams found this in 1964, for heapsort.

Push puts a number at the end and swaps it up while it is smaller than its parent (sift up). Pop takes the top, moves the last item to the top, then swaps it down with its smaller child while it is larger (sift down). Why the smaller child? After the swap, it is the parent of the other child, so it must be the smaller of the two.

Bottom: the real Python list. Amber: the item that moves. Blue: the item it is compared with. Teal: the rule holds. Red: leaves. Numbers 0–99, at most 15.

The sentence that keeps the code correct

Each parent is smaller than or equal to each of its children. So index 0 holds the smallest item.

This invariant holds after each push and pop. Why? Say the new item x swaps with its parent p, which has another child s. Before the push, p ≤ s. Now x is the parent of p and s, and x < p ≤ s. So the rule holds below x; the only problem moves up a row. Sift down works the same way, from the top: the item swaps with its smaller child, and the problem moves down one row.

You do not write sift up or sift down yourself: Python's heapq module does them. But heapq only keeps the smallest item on top. To keep the largest on top, put each number in with a minus sign. Then the largest number has the smallest value: 9, 4 and 1 go in as −9, −4 and −1, and −9 is on top. When you take an item out, put the minus sign back: −(−9) = 9.

import heapq
h = []
heapq.heappush(h, 5)       # sift up: about log2 n steps
h[0]                       # the smallest item: 1 step
heapq.heappop(h)           # sift down: about log2 n steps
heapq.heapreplace(h, 7)    # pop the smallest, then push 7: one sift
nums = [5, 3, 8]
heapq.heapify(nums)        # in place, about 2n steps; it returns None

Worked example 1: Kth Largest Element in a Stream (LeetCode 703)

Problem. You get k and a list nums. Then add(val) adds one number and returns the k-th largest so far. With k = 3 and [4, 5, 8, 2]: add(3) → 4, add(5) → 5, add(10) → 5, add(9) → 8, add(4) → 8.

The key fact. A number outside the top k now can never get in later: new numbers only push the bar up. So keep only the k largest, in a min-heap. Its top, h[0], is the gate: it is the answer, and it is the item to remove when a larger number comes in.

Not kept

The first four numbers are nums. Kept numbers are shown smallest first. Teal border: the gate. Not kept: red was removed, grey bounced off. Heap steps: 1 compare plus log2 k. Sort steps: about n moves per add (see Claim 2).

class KthLargest:
    def __init__(self, k, nums):
        self.k, self.heap = k, []          # the k largest numbers so far
        for x in nums:
            self.add(x)

    def add(self, val):
        if len(self.heap) < self.k:
            heapq.heappush(self.heap, val)
        elif val > self.heap[0]:           # beats the gate
            heapq.heapreplace(self.heap, val)
        return self.heap[0]                # smallest of the top k = the k-th largest

Each add is one comparison and at most one sift: about log2 k steps, for any stream length.

Worked example 2: Last Stone Weight (LeetCode 1046)

Problem. Each turn, smash the two heaviest stones. Equal weights both go; otherwise the difference stays. Return the last weight, or 0. [2, 7, 4, 1, 8, 1]: 8 and 7 leave 1; 4 and 2 leave 2; 2 and 1 leave 1; 1 and 1 go; the answer is 1.

def lastStoneWeight(stones):
    heap = [-s for s in stones]            # minus signs make a max-heap
    heapq.heapify(heap)
    while len(heap) > 1:
        first = -heapq.heappop(heap)       # heaviest
        second = -heapq.heappop(heap)      # next heaviest
        if first != second:
            heapq.heappush(heap, -(first - second))
    return -heap[0] if heap else 0

Worked example 3: Find Median from Data Stream (LeetCode 295)

Problem. Build addNum(num) and findMedian(), which returns the middle value (or the average of the two middle values).

The idea. Cut the numbers in two halves. Keep the smaller half in a max-heap and the larger half in a min-heap, so both tops sit at the middle. Two rules:

  • Each item in the smaller half ≤ each item in the larger half. A new number goes to the larger half only if it is larger than that half's top. When the sizes differ by 2, move one top across. A top is nearest the middle, so the rule holds.
  • The sizes differ by 1 or less. Then the median is the top of the bigger half, or the average of the two tops.

smaller half (max-heap) · top →← top · larger half (min-heap)

Amber: the number that moves. Teal: the two tops.

class MedianFinder:
    def __init__(self):
        self.small, self.large = [], []    # small: max-heap (negated); large: min-heap

    def addNum(self, num):
        if self.large and num > self.large[0]:
            heapq.heappush(self.large, num)
        else:
            heapq.heappush(self.small, -num)
        if len(self.small) > len(self.large) + 1:      # keep sizes within one
            heapq.heappush(self.large, -heapq.heappop(self.small))
        if len(self.large) > len(self.small) + 1:
            heapq.heappush(self.small, -heapq.heappop(self.large))

    def findMedian(self):
        if len(self.small) > len(self.large): return -self.small[0]
        if len(self.large) > len(self.small): return self.large[0]
        return (-self.small[0] + self.large[0]) / 2

Worked example 4: Merge K Sorted Lists (LeetCode 23)

Problem. Merge k sorted linked lists. [1→4→5, 1→3→4, 2→6] → 1→1→2→3→4→4→5→6.

The idea. The next answer item is the front of some list, so the heap holds the front node of each list. Pop the smallest, add it to the answer, and push the next node from the same list. With N nodes in all: about N × log2 k steps.

def mergeKLists(lists):                    # ListNode has .val and .next
    h = [(node.val, i, node) for i, node in enumerate(lists) if node]
    heapq.heapify(h)
    dummy = cur = ListNode()
    while h:
        _, i, node = heapq.heappop(h)      # the smallest front node
        cur.next = node; cur = node
        if node.next:                      # its list's next node takes its place
            heapq.heappush(h, (node.next.val, i, node.next))
    return dummy.next

Why the i? On equal values, Python compares the next tuple item, and two ListNode objects cannot be compared. Each list has one node in the heap, so (val, i) is unique.

Napkin math: how much does the heap save?

One operation is: take the smallest item out, then add a new item. The slider assumes 109 steps each second (compiled code; Python is about 100 times slower).

Claim 1, from PRINCIPLES.md: "heapify is O(n)." Half the items are in the bottom row and cannot move down; a quarter can move 1 row, an eighth 2 rows: n × (1/4 + 2/8 + 3/16 + …) = n moves at most. Each move down costs 2 comparisons: one to find the smaller child, and one to compare that child with the item. In Python, heapify of 100,000 items made 165,178 comparisons: 1.65 each, not 17 (log2 100,000). Verdict: accurate.

Claim 2: "for a stream, a heap of size k is much faster than a sort after each add." With 20,000 adds and k = 10: the list is sorted except for the new item, so Python's sort moves about n items: 20,0002 ÷ 2 = 2 × 108 moves in all. The heap: at most 20,000 × (1 + 4) = 100,000 steps. On the machine that built this page: 652 ms against 4 ms, 160 times faster. The step ratio is 2,000; the clock ratio is smaller because the sort moves items in large blocks of memory, which is much faster than one step at a time. Verdict: accurate.

Claim 3: "for the k-th largest of a fixed list, a heap beats a sort." For 1,000,000 numbers and k = 10, the sort is about 106 × 20 = 20 million steps, and the heap at most 106 × 5 = 5 million. On the clock, the sort took 258 ms and heapq.nlargest(10, nums) took 18 ms. A heap in a hand-written Python loop took 185 ms, because each pass of a Python loop is slow. Verdict: accurate. In Python, use nlargest.

If you need the full order only once, do not use a heap: sort (P9).

Common mistakes

  • The wrong heap for "keep the k best". The top must be the item you remove next. So the k largest need a min-heap, and the k smallest need a max-heap.
  • No tiebreaker in a tuple. Use (value, i, item), for the reason in worked example 4.
  • A lost minus sign on a negated heap, or h = heapq.heapify(h), which sets h to None.
  • A search in the heap. Any item except the top takes n steps to find.

Try it yourself

1. Push 0 into [1, 3, 2, 4, 9, 8, 6, 5, 7]. What is the list after?

0 starts at index 9 and swaps with 9, 3 and 1. Answer: [0, 1, 2, 4, 3, 8, 6, 5, 7, 9]. Check it: this is the first widget's start heap.

2. Which heap gives the k closest points to (0, 0)?

The top must be the largest kept distance: a max-heap of size k. Push (-(x*x + y*y), x, y) (squared distance keeps the order; integers always compare), and pop when the size is more than k.

In the real world

Compression, 1951. David Huffman, an MIT student, wrote a paper in place of a final exam. He found the best way to give short codes to common letters: again and again, join the two least common symbols. That is Last Stone Weight with the two smallest, so a min-heap. ZIP files and JPEG images still use his codes.

Maps. Dijkstra's route finder (P15) goes again and again to the nearest unfinished place. A research map of USA roads has about 24 million places and 58 million roads. Claim: "a heap makes this 100,000 times faster." A plain scan of all unfinished places at each step costs (2.4 × 107)2 ≈ 6 × 1014 steps, about 7 days at 109 steps each second. With a heap: about (24 + 58) million × 25 ≈ 2 × 109 steps, about 2 seconds. Ratio: 300,000. Verdict: approximately accurate, if anything low.
