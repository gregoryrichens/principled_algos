Principled Algos · Principle 10 of 18

Heap

You only need the smallest item. So keep only enough order to find it, and pay for nothing more.

Card 15 in DRILLS.md drills this page. P15 (weighted paths) uses a heap for Dijkstra's route finder.

As if to a child

A school nurse must always see the sickest kid first, and sick kids come in all day. She gives each kid a number: 1 means very sick, 9 means a little sick. She could put the kids in a line from 1 to 9, but then each new kid must find his place, and every kid behind him must step back. So she does something smarter. The kids stand in a pyramid, where each kid stands on two kids. The rule is: your number must not be bigger than the numbers of the two kids under you. Then the smallest number is always at the top.

A new kid starts at the bottom, and changes places with the kid above him while his number is smaller. When the top kid leaves, the last kid in the bottom row climbs to the top, then changes places with the smaller of the two kids under him until the rule is true again. A pyramid of 1,000 kids has only 10 rows, so each change needs 10 moves or less.

The extended explanation

The question a heap answers

Many programs keep a collection that changes all the time, and ask the same question about it again and again: "Which item is the smallest now?" Think of the timers in a web server: which one ends next?

Try the obvious tools first:

  • A list in no order. To add an item is easy: append it. But any item can be the smallest, so to find it you must look at all n items. That is n steps for each question.
  • A sorted list. Now the question is easy: the smallest item is at the front. But a new item must go to its correct place, and Python must move each item after that place by one position. To remove the front item, Python moves all the others. That is up to n steps for each change.

Each tool spends about n steps on one of the two operations, and we do both all the time. Where is the waste? The sorted list knows much more than we ask. It knows the second smallest item, the tenth, the 900th. We pay to keep all of that order correct, but we only read the front. So the real question is: what is the least order that still shows us the smallest item?

The least order that is enough

Put the items in a tree, with at most two children under each item. Then give the tree only one rule:

Each parent is smaller than or equal to each of its children.

This rule says nothing about two items side by side, or about cousins. It is a weak rule, but it is enough. Start at any item and walk up. At each step you go to a parent, and the parent is smaller or equal. So the values never get larger as you climb, and every path ends at the top. That makes the top smaller than or equal to every item in the tree. The smallest item is always at the top, and you read it in one step.

And a weak rule is cheap to repair. Count the rows: the top row has 1 item, then 2, then 4, then 8. Each row holds twice as many items as the row above, so the rows fill very fast. 10 rows hold about 1,000 items (210 = 1,024), and 20 rows hold about a million (220 = 1,048,576). In other words, n items need only about log2 n rows. You will see below that a change can only break the rule along one path from top to bottom. A path has one item in each row, so even with a million items, a repair touches about 20 of them.

That is the whole trick. A full order costs about n steps for each change. The rule "parent ≤ child" costs only about log2 n steps for each change, and it still shows us the smallest item. This tree is a heap. Because the smallest item is on top, it is a min-heap. A max-heap uses the opposite rule (parent ≥ child), so the largest item is on top. The top item is also called the root.

A tree with no links

A tree usually needs a link from each item to its children. A heap does not. Write the items into an ordinary list, row by row, from left to right: index 0 is the top, indexes 1 and 2 are the second row, and indexes 3 to 6 are the third row. Each row is full except the last, so the positions follow a fixed pattern. The children of index i are at 2i + 1 and 2i + 2, and its parent is at (i − 1) // 2. For example, index 4 has its children at 9 and 10, and its parent at 1. Simple arithmetic does the work of the links.

Two repairs: sift up and sift down

Push. Put the new item at the end of the list. That fills the next free place in the bottom row, so the tree keeps its shape. Now only one thing can be wrong: the new item can be smaller than its parent. If it is, swap them. In its new place, it may still be smaller than its new parent, so check again. Stop when the parent is smaller or equal, or when the item gets to the top. This is sift up. Each swap moves the item up one row, so it costs at most one comparison for each row.

Pop. The smallest item is at index 0, so take it out. That leaves a hole at the top. Fill it with the last item in the list, so the tree keeps its shape. But that item came from the bottom, so it is probably too large for the top. Compare it with its two children. If it is larger than the smaller child, swap them. Why the smaller one? After the swap, that child becomes the parent of the other child, and a parent must be the smaller of the two. Then do the same check one row lower. Stop when the item is smaller than or equal to its children, or when it has no children. This is sift down.

Why the repairs are enough

Before and after each push and pop, every parent is smaller than or equal to each of its children.

This is the invariant: the promise that the code keeps. It is easy to worry that a swap fixes one place and breaks another. So check sift up with care. Say the new item x is smaller than its parent p, and p has another child, s. The rule was true before the push, so p ≤ s. After the swap, x is the parent of both p and s. We know x < p, and p ≤ s, so x < s too. Both children of x are correct. And p is now in the old place of x: its children there (if any) came from below p, so they were already ≥ p. The only place where the rule can still fail is between x and its new parent, one row higher. So each swap moves the problem up one row, and the problem disappears at the top. Sift down works the same way in the other direction, and it depends on the choice of the smaller child c. After the swap, c is the parent of the moving item and of its own old sibling. c is smaller than the moving item (that is why they swapped), and c ≤ its sibling (that is why we chose it). So the rule holds at c, and the problem moves down one row, until it disappears at the bottom.

Heaps in Python

You do not write sift up and sift down yourself. Python's heapq module does them for you, on an ordinary list:

import heapq
h = []
heapq.heappush(h, 5)       # add an item, then sift up: about log2 n steps
heapq.heappush(h, 2)
h[0]                       # read the smallest item (2): 1 step
heapq.heapreplace(h, 7)    # FIRST remove the smallest (2), THEN add 7, with one sift
heapq.heappop(h)           # remove the smallest (5), then sift down: about log2 n steps
nums = [5, 3, 8]
heapq.heapify(nums)        # make a list into a heap in place: about 2n steps; it returns None

heapq makes a min-heap. (Python 3.14 added heappush_max and related functions, but many interview judges run older versions.) For a max-heap, the safe method is a minus sign. Put −x into the heap in place of x. Then the largest number becomes the smallest value in the heap: 9, 4 and 1 go in as −9, −4 and −1, and −9 is on top. When you take an item out, put the minus sign back: −(−9) = 9.

Worked example 1: Kth Largest Element in a Stream (LeetCode 703)

Problem. You get a number k and a list nums. Then each call add(val) adds one number and returns the k-th largest number so far. With k = 3 and nums = [4, 5, 8, 2], the calls add(3), add(5), add(10), add(9) and add(4) return 4, 5, 5, 8 and 8.

The slow way. Keep every number in a list. After each add, sort the list and read the k-th number from the end. Each add costs a sort, and the list grows forever.

Where the work goes. The sort puts all the numbers in order, but we read only one. Now think about a number that is not in the top k. Can it ever become the answer later? No. Once k numbers are kept, call the k-th largest so far the gate. Each new number is either not larger than the gate, so it does not matter, or it enters the top k and pushes the smallest of them out. So the gate never goes down, and a number that is below the gate can never come back. We can forget it.

The fix. Keep only the k largest numbers so far. Which of them do we need quickly? Two things: the answer, which is the smallest of the kept numbers, and the number to throw out when a larger one comes, which is also the smallest of the kept numbers. So keep the k largest numbers in a min-heap. Its top, h[0], is the gate. A new number gets in only if it is larger than the gate, and then the gate goes out. A min-heap for the largest numbers sounds backwards, until you remember that the top of a heap is always the item you remove next.

class KthLargest:
    def __init__(self, k, nums):
        self.k = k
        self.heap = []                     # the k largest numbers so far
        for x in nums:
            self.add(x)

    def add(self, val):
        if len(self.heap) < self.k:
            heapq.heappush(self.heap, val) # not full yet: keep it
        elif val > self.heap[0]:
            heapq.heapreplace(self.heap, val)   # beats the gate: the gate goes out
        return self.heap[0]                # the smallest of the top k is the k-th largest

heapreplace removes the top before it adds the new number. That is why the code calls it only after val > self.heap[0]. Each add is one comparison with the gate, and at most one sift in a heap of k items. That is about log2 k steps, no matter how long the stream is.

Worked example 2: Find Median from Data Stream (LeetCode 295)

Problem. Build two methods. addNum(num) adds a number. findMedian() returns the middle value of all numbers so far, or the average of the two middle values when the count is even. After adding 5, 15, 1 and 3, the median is (3 + 5) / 2 = 4.

The idea. A heap shows you one end of a collection, but the median is in the middle. So cut the numbers into two halves at the middle: a smaller half and a larger half. The median is at the place where the two halves touch. It is the largest number of the smaller half, or the smallest number of the larger half, or the average of the two. So each half must show us its number nearest the middle. Keep the smaller half in a max-heap, so its largest number is on top. Keep the larger half in a min-heap, so its smallest number is on top. The two tops face each other across the middle.

Two rules keep this picture true:

  • Order. Every number in the smaller half is smaller than or equal to every number in the larger half. When a new number comes, compare it with the top of the larger half. If it is larger, it goes into the larger half. If not, it goes into the smaller half.
  • Balance. The sizes of the halves differ by one or less. After an add, if one half has two more numbers than the other, move its top across. The top is the number nearest the middle, so the move does not break the order rule.

With both rules true, the median is easy to read. If one half is bigger, its top is the median. If the halves are equal, the median is the average of the two tops.

class MedianFinder:
    def __init__(self):
        self.small = []                    # the smaller half: a max-heap, stored with minus signs
        self.large = []                    # the larger half: a min-heap

    def addNum(self, num):
        if self.large and num > self.large[0]:
            heapq.heappush(self.large, num)          # order rule
        else:
            heapq.heappush(self.small, -num)
        if len(self.small) > len(self.large) + 1:    # balance rule
            heapq.heappush(self.large, -heapq.heappop(self.small))
        if len(self.large) > len(self.small) + 1:
            heapq.heappush(self.small, -heapq.heappop(self.large))

    def findMedian(self):
        if len(self.small) > len(self.large):
            return -self.small[0]
        if len(self.large) > len(self.small):
            return self.large[0]
        return (-self.small[0] + self.large[0]) / 2

Each add does at most three pushes and pops, so it costs about log2 n steps. Each median reads one or two tops: 1 step.

Where else it shows up

  • Last Stone Weight (1046). Again and again, smash the two heaviest stones and put back the difference if it is not 0. We need the largest items again and again while the collection changes, so use a max-heap with minus signs.
  • Merge K Sorted Lists (23). Each list is sorted, so the smallest item not yet used in all the lists is the first unused node of one list. Keep those k nodes in a min-heap. Pop the smallest, add it to the answer, and push the next node of the same list. In the code below, i is the number of the list, and it is the tiebreaker from Common mistakes. 
    def mergeKLists(lists):
    h = [(node.val, i, node) for i, node in enumerate(lists) if node]
    heapq.heapify(h)
    dummy = cur = ListNode()
    while h:
        _, i, node = heapq.heappop(h)
        cur.next = node
        cur = node
        if node.next:
            heapq.heappush(h, (node.next.val, i, node.next))
    return dummy.next
  • Kth Largest Element in an Array (215). Worked example 1, on a fixed list. In Python, heapq.nlargest(k, nums)[-1] does it in one line.
  • K Closest Points to Origin (973). Keep the k smallest distances. The item to throw out is the largest kept distance, so you need a max-heap of size k: push (-(x*x + y*y), x, y). Only the first item of the tuple gets the minus sign, because only it decides the order.
  • Not a heap: if you need the full order only once, sort (P9).

How to recognize a heap problem. The problem asks for the k-th or the top k items; or for the smallest or largest item again and again while items come and go; or to merge k sorted lists; or for the next event in time.

Napkin math: is heapify really O(n)?

PRINCIPLES.md claims that heapify turns a list into a heap in O(n) steps, which means "in a number of steps that grows in proportion to n". That sounds too good. If you push the n items one at a time, each push can cost up to log2 n steps in the worst case: 17 for 100,000 items.

heapify works differently. It goes from the last parent (index n // 2 − 1) back to index 0, and sifts each item down. This order is correct because when it reaches an item, both trees under it are already heaps, so one sift down repairs the item. And an item can only sift down as far as there are rows under it. About half of the items are leaves, with no children, so they do not move at all. About a quarter can move down 1 row, an eighth 2 rows, a sixteenth 3 rows. Add it up: n × (1/4 + 2/8 + 3/16 + 4/32 + …) = n × 1. So there are at most about n moves, and each move costs 2 comparisons (one to find the smaller child, one to compare it with the item): about 2n comparisons in all.

A count in Python agrees: heapify on 100,000 random numbers made 165,178 comparisons, 1.65 for each item. The claim is accurate.

Common mistakes

  • The wrong kind of heap for "keep the k best". The top of the heap must be the item you throw out next. To keep the k largest, use a min-heap. To keep the k smallest, use a max-heap.
  • No tiebreaker in a tuple. Python compares tuples one item at a time. If two values are equal, it compares the next item, and it cannot compare objects such as list nodes, so the program stops with an error. Put a unique number between them: (value, i, item).
  • A search in the heap. A heap only knows where its top is. To find or remove any other item, you must look at all n items.
  • h = heapq.heapify(h). heapify changes the list in place and returns None, so this line sets h to None.

In the real world

Huffman codes, 1951. David Huffman was a graduate student at MIT, in a class taught by Robert Fano. Fano gave the students a choice: take the final exam, or solve a hard problem in a term paper. The problem was to find the shortest way to write a message in 0s and 1s, when you know how often each letter is used. Fano himself had worked on it without a full solution, and Huffman nearly gave up. Then he found a simple method: take the two least common symbols, join them into one symbol whose count is the sum of the two, and do it again until one symbol is left. Each join adds one bit to the codes of the letters inside it, so rare letters get long codes and common letters short ones. "Take the two smallest and put back their sum" has the same shape as Last Stone Weight (in "Where else"), but with a min-heap. Huffman published the method in 1952. ZIP files and JPEG images still use Huffman codes.
