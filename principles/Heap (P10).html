Heap

Some programs must find the smallest item again and again, while items come and go. A heap does this fast.

Card 15 in DRILLS.md has practice drills for this page. You do not need it to read this page.

As if to a child

A school nurse must always see the sickest kid first, and sick kids come in all day. She gives each kid a number: 1 means very sick, 9 means a little sick. So she always wants the kid with the smallest number.

She could put the kids in a line from 1 to 9. But then each new kid must find his place in the line, and every kid behind that place must step back. That is a lot of moving.

So she makes a pyramid. Each kid stands on two kids. The top row has 1 kid, the next row has 2, then 4, then 8, because each row has twice as many kids as the row above. There is one rule: your number must not be bigger than the numbers of the two kids under you. Then the smallest number is always at the top, and the nurse sees it at once.

A new kid joins at the end of the bottom row. If his number is smaller than the number of the kid above him, they change places. He checks again, and again, until the kid above him has a smaller or equal number. When the top kid goes to the nurse, the pyramid has one kid fewer, so one place must become empty. To keep the pyramid with no gaps, the empty place must be the end of the bottom row. So the kid at the end of the bottom row must move anyway, and the only free place is the top. He climbs to the top. Then he changes places with the smaller of the two kids under him. (If he changed places with the bigger one, that kid would stand on top of a smaller number, and the rule would break.) He does this again and again, until the rule is true. Because the rows double, 1,000 kids fit in only 10 rows (1 + 2 + 4 + … + 512 = 1,023). So a kid never needs to change places more than 9 times.

The extended explanation

The question a heap answers

Many programs keep a collection that changes all the time, and ask the same question about it again and again: "Which item is the smallest now?" A hospital list asks "who is most urgent?" A game asks "which event happens next?" Items come in, the smallest goes out, more items come in.

On this page, n is the number of items in the collection. Try the obvious tools first:

  • A list in no order. To add an item is easy: append it to the end. But any item can be the smallest, so to find it you must look at all n items. That is n steps each time you ask.
  • A sorted list. Now the question is easy: the smallest item is at the front. But a new item must go into its correct place, and Python must move each item after that place along by one position. To remove the front item, Python moves all the others forward. That is up to n steps each time the list changes.

Each tool is slow at one of the two jobs, and we do both jobs all the time. Where is the waste? Look at the sorted list. It knows much more than we ask. It knows the second smallest item, the tenth, the 900th. We pay to keep all of that order correct, but we only ever read the front. So the real question is: what is the least order that still shows us the smallest item?

The least order that is enough

Put the items in a tree. A tree here is like a family tree drawn from the top down: each item can have up to two items under it. The item above is the parent, and the items under it are its children. The item at the very top is the root. Fill the tree row by row, from left to right, with no gaps. (The first widget below draws one.)

Now give the tree only one rule:

Each parent is smaller than or equal to each of its children.

The rule says nothing about two items side by side. It is a weak rule, but it is enough. Start at any item and walk up, one parent at a time. Each parent is smaller or equal, so the values never get larger as you climb, and every walk ends at the root. So the root is smaller than or equal to every item in the tree. The smallest item is always at the root, and you can read it in one step.

And a weak rule is cheap to repair, because the tree is short. Count the items in each row: 1, then 2, then 4, then 8. Each row holds twice as many items as the row above, so the rows fill very fast. 10 rows hold up to 1,023 items, and 20 rows hold over a million. Mathematicians write this as "n items need about log2 n rows". log2 n means: how many times must you double 1 to get to n? For 1,000, the answer is about 10, because 2 × 2 × … (10 times) = 1,024.

You will see below that a repair only walks along one path from the root to the bottom, with one item in each row. So even with a million items, a repair touches about 20 of them. A sorted list can need a million moves for the same change.

This tree is a heap. Because the smallest item is on top, it is called a min-heap. A max-heap uses the opposite rule (each parent is larger than or equal to its children), so the largest item is on top.

A tree that is only a list

You might expect that each item needs some way to point at its children. A heap does not need that. Write the items into an ordinary Python list, row by row, from left to right:

Because there are no gaps, each item's children are always in the same places. The children of index 0 are 1 and 2. The children of index 1 are 3 and 4. The children of index 2 are 5 and 6. The pattern is: the children of index i are at 2*i + 1 and 2*i + 2. Check it: for i = 2, that gives 5 and 6.

Go the other way to find a parent: the parent of index i is at (i - 1) // 2. In Python, // divides and throws away the remainder, so 7 // 2 is 3. Check it: index 6 has parent (6 - 1) // 2 = 5 // 2 = 2, and index 5 has parent 4 // 2 = 2. Both are children of index 2, as the table says.

Two repairs: sift up and sift down

Push (add an item). Put the new item at the end of the list. That is the next free place in the bottom row, so there are still no gaps. Now only one thing can be wrong: the new item can be smaller than its parent. If it is, swap them. In its new place, it may still be smaller than its new parent, so check again. Stop when the parent is smaller or equal, or when the item is at the root. This is called sift up. Each swap moves the item up one row, so a push needs at most one comparison for each row.

Pop (take out the smallest). The smallest item is at index 0, so take it out. That leaves a hole at the root. Fill it with the last item in the list, so there are still no gaps. But that item came from the bottom, so it is probably too large for the top. Compare it with its two children, and find the smaller child. If the item is larger than that child, swap them. Then do the same check one row lower. Stop when the item is smaller than or equal to its children, or when it has no children. This is called sift down.

Why move the last item to the top, if it will probably sink back down? Because the list must stay with no gaps. After a pop there is one item fewer, so the last place in the list must become empty, and the item in it must go somewhere. The only free place is the hole at the top. You could fill the hole another way: move the smaller child up, then the smaller grandchild, and so on. But then the hole ends in the bottom row, usually not at the last place, so you still must move the last item into it and check it against its parent. Both ways walk one path from top to bottom, so both cost about log2 n steps. Python's heapq uses the second way, because the last item usually belongs near the bottom, and that saves some comparisons. This page and the widget use the first way, because it is simpler to describe.

Try both in the widget. Type 0 and press Push: watch 0 climb to the top. Then press Pop smallest: watch the last item move to the top and fall back down.

Why a swap never breaks the rule somewhere else

A careful reader will worry: a swap fixes one parent and child, but can it break the rule between other items? Look at a real swap. Press Reset in the widget, then push 0. 0 first swaps with 9 and climbs to index 4. Now its parent is index 1, which holds 3. The other child of index 1 is index 3, which holds 4. Before the push, the rule was true, so 3 ≤ 4.

Now 0 and 3 swap. 0 becomes the parent of 3 and of 4. Is the rule true for both children? 0 is smaller than 3 (that is why they swapped), and 3 is smaller than or equal to 4 (the rule was true before), so 0 is smaller than 4 too. Both children are fine. And 3 moved down to index 4, where its child is 9. Before the swap, 9 was also under 3, two rows down, and values never get smaller as you go down, so 3 ≤ 9. That is fine too. The only place where the rule can still fail is between 0 and its new parent, one row higher. So each swap moves the possible problem up one row, and at the root there is nothing above to check.

Sift down needs the smaller child for the same reason. After you push 0, press Pop smallest. 0 leaves, 9 moves to the root, and its children are 1 and 2. If 9 swaps with 1, then 1 becomes the parent of 9 and 2, and that is correct. If 9 swapped with 2 instead, then 2 would become the parent of 1, and 2 is larger than 1: the rule would break.

A rule that is true before and after every operation is called an invariant. The heap's invariant is the rule "each parent ≤ each of its children".

Heaps in Python

You do not write sift up and sift down yourself. Python's heapq module (a file of ready-made code that you load with import) does them for you, on an ordinary list:

import heapq
h = []
heapq.heappush(h, 5)       # add 5, then sift up
heapq.heappush(h, 2)       # add 2, then sift up: 2 goes to the top
print(h[0])                # prints 2: the smallest item is always h[0]
print(heapq.heappop(h))    # takes out and prints 2, then sifts down
heapq.heapreplace(h, 7)    # puts 7 in the place of the smallest (5), sifts down once, returns 5
nums = [5, 3, 8]
heapq.heapify(nums)        # makes nums into a heap (see Napkin math below)

heapify works in place: it changes the list you give it, and it does not make a new list. It returns None.

heapq only makes min-heaps. When you want the largest item on top, use a minus sign. Put −x into the heap in place of x. Then the largest number becomes the smallest value in the heap: 9, 4 and 1 go in as −9, −4 and −1, and −9 is on top, because −9 is the smallest of them. When you take an item out, put the minus sign back: −(−9) = 9. (Python 3.14 added max-heap functions, but many practice websites still run older versions of Python, so the minus sign is the safe method.)

About the worked examples

The worked examples are problems from LeetCode, a website with practice problems for coding interviews. Each problem has a number. These two problems ask you to write a class. A class bundles some data together with the functions that use it. Its functions are called methods. Here is a tiny class:

class Counter:
    def __init__(self, start):     # runs once, when you make the object
        self.total = start         # self.total stays alive between calls

    def add(self, x):              # a method
        self.total += x
        return self.total

c = Counter(10)                    # runs __init__ with start = 10
print(c.add(5))                    # prints 15
print(c.add(1))                    # prints 16: it remembers the 15

c = Counter(10) makes an object: one bundle of data, built from the class. A few rules:

  • Every method has self as its first parameter, and Python fills it in for you. When you write c.add(5), Python runs add with self = c and x = 5. So the def line has two parameters, but the call gives only one value.
  • Inside a method, self. reaches the object's data and its other methods. self.total is the object's total. A method can also call another method of the same object, for example self.add(3).
  • The data stays. A normal function forgets its variables when it returns. An object keeps its data in self, so each call can use what the earlier calls left.

That is why these problems use a class: each answer depends on all the numbers from the earlier calls.

Worked example 1: Kth Largest Element in a Stream (LeetCode 703)

The problem in plain words. Numbers come to you one at a time. (A flow of numbers that arrive one at a time is called a stream.) After each new number, you must say which number is the 3rd largest of all the numbers you have seen so far. The problem calls the position k, so it can also ask for the 1st, the 2nd or the 10th largest. In our example, k = 3.

What "the k-th largest" means. Write all the numbers you have so far in order, from largest to smallest. The k-th largest is the number at position k in that order. Equal numbers each take their own position. For example:

  • After 4, 5, 8, 2, 3, the order is 8, 5, 4, 3, 2. The 1st largest is 8, the 2nd is 5, and the 3rd largest is 4.
  • After 4, 5, 8, 2, 3, 5, the order is 8, 5, 5, 4, 3, 2. Now the 3rd largest is 5, because the two 5s take positions 2 and 3.

How LeetCode asks it. LeetCode gives you k and a list of starting numbers, nums, when it makes your object: KthLargest(k, nums). The starting numbers return nothing. Then LeetCode calls add(val) once for each new number, and each add must return the k-th largest of all the numbers so far, including nums. Here is the example, with the answer worked out for each call:

The slow way. Do exactly what the table does. Keep every number in a list, sort it after each add, and read position 3. This works, but the list grows forever, and each add sorts all of it.

Look at the table again. We only ever read the first three numbers of each row. What happens to a number after position 3? Look at 2: it is at position 4 after the start, and it only moves further down. Each new number goes in somewhere, and that can only push the numbers after it down the order. Nothing ever pushes a number up. So a number that is not in the top 3 now will never be in the top 3 again. We can forget it, and keep only the top 3.

Which of the top 3 do we need? The answer is the 3rd largest. In the top 3, the 3rd largest is the smallest of the three. After add(3), the top 3 are 8, 5 and 4, and the answer, 4, is the smallest of them.

Now a new number arrives. Compare it with that smallest kept number:

  • It is not larger. Then at least 3 numbers are as large or larger, so the new number lands at position 4 or lower. Forget it. Example: add(4) at the end. The kept numbers are 10, 9 and 8, and 4 is not larger than 8.
  • It is larger. Then it enters the top 3, and the smallest kept number drops to position 4. Throw that one out. Example: add(10). The kept numbers are 8, 5 and 5. 10 is larger than 5, so 10 goes in and one 5 goes out, and the kept numbers become 10, 8 and 5.

So in every step, the number we compare with, the number we throw out, and the answer are the same number: the smallest of the kept numbers. That is the job of a min-heap. Keep the top k numbers in a min-heap, and that number is always at h[0]. Call it the gate, because a new number must be larger than it to get in. (A min-heap for the largest numbers sounds backwards. It is not, because the top of a heap is always the item you take out next.)

In "All so far", the teal numbers are the top k, and the one with the teal border is the k-th largest. Grey numbers are not in the top k, and the heap has forgotten them. In "Heap list h", the teal border marks h[0], the gate.

Here is the code. Each part matches a step above:

import heapq

class KthLargest:
    def __init__(self, k, nums):
        self.k = k
        self.heap = []                          # the top k numbers so far
        for x in nums:
            self.add(x)                         # the start numbers use the same rules

    def add(self, val):
        if len(self.heap) < self.k:
            heapq.heappush(self.heap, val)      # fewer than k kept: keep it
        elif val > self.heap[0]:
            heapq.heapreplace(self.heap, val)   # larger than the gate: gate out, val in
        return self.heap[0]                     # the smallest kept number = the k-th largest

Three details:

  • __init__ calls self.add(x) for each start number, so the start numbers follow the same rules. add returns a value each time, but __init__ does not use it, because the start numbers return nothing.
  • heapreplace puts the new number straight into the place of the top item, h[0], then repairs the heap with one sift down. It does not compare the new number with the old top first: the old top always goes out. So the code calls it only after it checks val > self.heap[0]. Without that check, a small number would push out the gate and take its place, and the answer would be wrong.
  • LeetCode promises that each add happens when there are at least k numbers in all, so self.heap[0] is always a real answer. (The widget shows "—" if you break that promise.)
  • If the number is not larger than the gate, neither branch runs, so the heap does not change. That is "forget it".

The cost. Each add does one comparison, and at most one sift in a heap of k items. A sift touches one item in each row, so it is at most about log2 k steps: 2 steps for k = 3. That stays the same however long the stream gets. The slow way sorts a list that grows with every number.

Worked example 2: Find Median from Data Stream (LeetCode 295)

The problem in plain words. Numbers come to you one at a time. At any time, you may be asked for the median of all the numbers so far. To find the median, write the numbers in order from smallest to largest. If there is an odd count, the median is the middle number. If there is an even count, the median is the average of the two middle numbers. For example, after 5, 15, 1 and 3, the order is 1, 3, 5, 15. The two middle numbers are 3 and 5, so the median is (3 + 5) / 2 = 4.

You write a class with two methods: addNum(num) adds a number, and findMedian() returns the median.

The idea. A heap shows you one end of a collection, but the median is in the middle. So cut the numbers into two halves at the middle: a smaller half and a larger half. The median is where the two halves touch: it is the largest number of the smaller half, or the smallest number of the larger half, or the average of those two. So each half must show us its number nearest the middle. Keep the smaller half in a max-heap, so its largest number is on top. Keep the larger half in a min-heap, so its smallest number is on top. The two tops face each other across the middle.

Two rules keep this picture true:

  • Order. Every number in the smaller half is smaller than or equal to every number in the larger half. So when a new number comes, compare it with the top of the larger half, which is the smallest number of that half. If the new number is larger, it belongs with the larger half. If not, it is smaller than or equal to every number in the larger half, so it can safely go into the smaller half.
  • Balance. The sizes of the halves differ by one or less. After an add, if one half has two more numbers than the other, move its top across. The top is the number nearest the middle, so the move does not break the order rule.

With both rules true, the median is easy to read. Say there are 5 numbers, 3 in one half and 2 in the other. In order from smallest to largest, the middle number is the 3rd one, and it sits at the edge of the bigger half, next to the other half: that is the bigger half's top. So if one half has one more number, its top is the median. If the halves are the same size, the median is the average of the two tops. Here are the four numbers from the example. (In Python, / always gives a decimal number, so the code returns 10.0 and 4.0.)

Amber is the number that moves. Teal marks the two tops. "Not balanced yet" means that a top must move across before the median is correct.

import heapq

class MedianFinder:
    def __init__(self):
        self.small = []                    # the smaller half: a max-heap, stored with minus signs
        self.large = []                    # the larger half: a min-heap

    def addNum(self, num):
        if self.large and num > self.large[0]:
            heapq.heappush(self.large, num)          # order rule
        else:
            heapq.heappush(self.small, -num)
        if len(self.small) > len(self.large) + 1:    # balance rule
            heapq.heappush(self.large, -heapq.heappop(self.small))
        if len(self.large) > len(self.small) + 1:
            heapq.heappush(self.small, -heapq.heappop(self.large))

    def findMedian(self):
        if len(self.small) > len(self.large):
            return -self.small[0]
        if len(self.large) > len(self.small):
            return self.large[0]
        return (-self.small[0] + self.large[0]) / 2

Three details:

  • if self.large and ...: an empty list counts as false in Python, so this first checks that the larger half is not empty.
  • The smaller half stores each number with a minus sign, so 5 is stored as −5. In the balance line, heapq.heappop(self.small) takes out the most negative value, for example −5, which stands for the largest number of the smaller half, 5. The minus sign in front makes it 5 again, and 5 goes into the larger half. The last balance line does the opposite. In the widget's run, when 7 is added, the larger half has 4 numbers (5, 7, 8, 15) and the smaller half has 2. So this line takes out 5, the smallest of the larger half, and stores it as −5 in the smaller half.
  • findMedian puts the minus sign back when it reads self.small[0].

The cost. Each add does at most three pushes and pops, so it costs about log2 n steps. Each median only reads one or two tops: 1 step.

Where else it shows up

The numbers are LeetCode problem numbers.

  • Last Stone Weight (1046). You have stones of different weights. Again and again, smash the two heaviest stones together. If they weigh the same, both are destroyed. If not, the heavier one stays, with the difference as its new weight. You need the two largest items again and again while the collection changes, so use a max-heap, with minus signs.
  • Kth Largest Element in an Array (215). Worked example 1, but all the numbers come at once, in one list. In Python, heapq.nlargest(k, nums) returns the k largest numbers, largest first, so heapq.nlargest(k, nums)[-1] (the last of them) is the k-th largest.
  • K Closest Points to Origin (973). You get points (x, y), and you must return the k points closest to (0, 0). This is worked example 1 turned around: you keep the k smallest distances, so the number to throw out is the largest kept distance. That needs a max-heap of size k. Push a tuple (a fixed group of values in parentheses) for each point: (-(x*x + y*y), x, y). Python orders tuples by their first value, so only the first value gets the minus sign. x*x + y*y is the distance squared: it has the same order as the distance, and it needs no square root.
  • Merge K Sorted Lists (23). You get k sorted lists and must join them into one sorted list. The smallest item that is not used yet is always at the front of one of the lists. So keep the front item of each list in a min-heap. Take out the smallest, add it to the answer, and push the next item from the same list. (On LeetCode, the lists are linked lists, which this page does not teach. Card 15 in DRILLS.md has the code.)
  • Not a heap: if you need the whole order only once, just sort the list.

How to recognize a heap problem. The problem asks for the k-th or the top k items; or for the smallest or largest item again and again while items come and go; or to merge sorted lists; or for the next event in time.

Napkin math: why is heapify so fast?

There are two ways to make a heap from n numbers. You can push them one at a time. Or you can call heapify, which is often said to be much faster: its work grows in step with n (twice the numbers, about twice the work). Is that true? Count the moves, for a full tree of 10 rows with 1,023 items.

Push one at a time. In the worst case, each new item climbs all the way to the root. An item in row 10 can climb 9 rows, an item in row 9 can climb 8 rows, and so on. Most items are in the bottom rows, so most items can climb far:

512 × 9 + 256 × 8 + 128 × 7 + 64 × 6 + 32 × 5 + 16 × 4 + 8 × 3 + 4 × 2 + 2 × 1 = 8,194 moves.

heapify. It starts with the items in the order they are. The items in the bottom row have nothing under them, so they need no work. So heapify starts at the last item that has a child, and works back to the root. It sifts each of these parents down. (When it gets to an item, the items under it already follow the rule, so one sift down is enough.) Now the big rows are the lucky ones. The 512 items in row 10 have no children, so they cannot move. An item in row 9 can move down 1 row, an item in row 8 can move down 2 rows, and so on:

512 × 0 + 256 × 1 + 128 × 2 + 64 × 3 + 32 × 4 + 16 × 5 + 8 × 6 + 4 × 7 + 2 × 8 + 1 × 9 = 1,013 moves.

That is fewer moves than items. The trick is that most items are near the bottom, and in heapify they have almost nowhere to go. Now count comparisons. At each row, a sift down needs at most 2 comparisons: one to find the smaller child, and one to compare that child with the item. Each of the 511 parents also has one last check, where it stops. So the worst case is 2 × 1,013 + 2 × 511 = 3,048 comparisons for 1,023 items: fewer than 3 for each item. In a real test in Python, heapify on 100,000 random numbers made 165,178 comparisons, about 1.65 for each number. That is lower than 3, because on random numbers most sifts stop early. Verdict: the claim is accurate.

Common mistakes

  • The wrong kind of heap for "keep the k best". The top of the heap must be the item you throw out next. To keep the k largest, use a min-heap. To keep the k smallest, use a max-heap.
  • No tiebreaker in a tuple. Python compares tuples one value at a time. If the first values are equal, it compares the second values. If the second value is something that Python cannot compare with <, such as a dictionary, the program stops with an error. So put a unique number second: (value, i, item), where i is different for each item.
  • A search in the heap. A heap only knows where its smallest item is. To find or remove any other item, you must look at all n items.
  • h = heapq.heapify(h). heapify changes the list in place and returns None, so this line sets h to None. Write heapq.heapify(h) alone.

In the real world

Huffman codes, 1951. David Huffman was a graduate student at MIT, in a class taught by Robert Fano. Fano gave the students a choice: take the final exam, or solve a hard problem in a term paper. The problem was to find the shortest way to write a message in 0s and 1s (each 0 or 1 is called a bit), when you know how often each letter is used. Fano himself had worked on it without a full solution, and Huffman nearly gave up. Then he found a simple method. Take the two least common letters, join them into one group whose count is the sum of the two, and do it again until one group is left. Each join adds one bit to the code of each letter inside it. Rare letters are joined early and often, so they get long codes. Common letters are joined late, so they get short codes. "Take the two smallest and put back their sum" is a min-heap job, with the same shape as Last Stone Weight. Huffman published the method in 1952, and ZIP files and JPEG images still use Huffman codes today.
